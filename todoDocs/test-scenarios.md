## 1. 테스트 환경 설정

### 1.1 사전 준비사항

```bash
# Backend 실행
cd backend
./mvnw spring-boot:run

# Frontend 실행
cd frontend
npm run dev

# 접속 URL
Frontend: http://localhost:5173
Backend API: http://localhost:8080
```

### 1.2 테스트 데이터 준비

- 회사 데이터: 최소 1개 회사 등록 필요
- 부서 데이터: 회계팀, 인사팀, 영업팀 등록 필요
- 계정과목: 기본 계정과목 트리 구조 생성 필요

## 3. 인증 및 권한 테스트

### 3.1 로그인 테스트

#### TC-AUTH-001: 정상 로그인
**목적**: 유효한 계정으로 로그인 성공
**권한**: 모든 권한
**절차**:
1. 로그인 페이지 접속 (`/login`)
2. 이메일 입력: `admin@erp.com`
3. 비밀번호 입력: `admin123!`
4. "로그인" 버튼 클릭

**예상 결과**:
- ✅ 로그인 성공
- ✅ 대시보드 페이지로 리다이렉트
- ✅ 상단 네비게이션에 사용자 이름 표시
- ✅ localStorage에 토큰 저장 확인

---

#### TC-AUTH-002: 잘못된 비밀번호
**목적**: 잘못된 비밀번호로 로그인 실패
**권한**: N/A
**절차**:
1. 로그인 페이지 접속
2. 이메일 입력: `admin@erp.com`
3. 비밀번호 입력: `wrongpassword`
4. "로그인" 버튼 클릭

**예상 결과**:

- ❌ "이메일 또는 비밀번호가 올바르지 않습니다" 오류 메시지
- ❌ 로그인 페이지 유지

---

- ✅ 검색 기능 UI 표시

---

**목적**: 이름으로 사원 검색
**권한**: 모든 권한
**절차**:

- ✅ 뒤로가기 버튼으로 목록으로 복귀 가능

### 4.2 사원 등록 테스트

- ✅ "사원이 등록되었습니다" 성공 메시지
- ✅ 사원 목록 페이지로 리다이렉트

- ❌ 또는 API 직접 호출 시 403 Forbidden 응답

---

#### TC-JE-019: APPROVED → POSTED (전기)
**목적**: 승인된 전표 전기 (계정 잔액 반영)
**권한**: ADMIN, MANAGER
**절차**:
1. MANAGER 계정으로 로그인
2. APPROVED 상태 전표 상세 페이지에서 "전기" 버튼 클릭
3. 확인 다이얼로그 확인 (경고: "전기 후에는 수정이 불가능합니다")
4. "전기" 버튼 클릭

**예상 결과**:
- ✅ "전표가 전기되어 계정 잔액에 반영되었습니다" 성공 메시지

- ✅ 전기일시 표시
- ✅ 모든 액션 버튼 사라짐 (읽기 전용)
- ✅ 관련 계정의 차변/대변 잔액 업데이트 확인

---

#### TC-JE-020: 전기 후 계정 잔액 확인
**목적**: 전기 시 계정 잔액 정확한 반영 검증
**권한**: 모든 권한
**사전조건**: TC-JE-019 완료
**절차**:
1. 전기한 전표의 분개 항목에서 사용된 계정 확인
2. 계정과목 상세 페이지에서 해당 계정의 잔액 확인

**예상 결과**:
- ✅ 차변 계정: 차변 잔액 증가
- ✅ 대변 계정: 대변 잔액 증가
- ✅ 잔액 = 이전 잔액 + 전표 금액

**예시**:
- 전표: 현금(차변 100,000) / 매출(대변 100,000)
- 현금 계정: 차변 잔액 +100,000
- 매출 계정: 대변 잔액 +100,000

## 7. 통합 시나리오 테스트

### 7.1 엔드투엔드 시나리오

#### TC-E2E-001: 신규 사원 입사부터 급여 전표 입력까지
**목적**: 전체 시스템 플로우 검증
**권한**: ADMIN
**시나리오**:

**1단계: 신규 사원 등록**
1. ADMIN으로 로그인
2. 사원 관리 > 사원 등록
3. 사원 정보 입력:
   - 이름: 신입사원
   - 이메일: newbie@erp.com
   - 부서: 회계팀
   - 직급: 사원
   - 월급여: 3,000,000원

**2단계: 계정과목 확인/설정**
1. 회계 관리 > 계정과목
2. "급여" 계정 존재 여부 확인
3. 없으면 "급여" 계정 추가 (계정 유형: EXPENSE)

**3단계: 급여 전표 입력**
1. 회계 관리 > 전표 관리
2. 전표 입력 클릭
3. 분개 라인 입력:
   - 행 1: 급여(차변) 3,000,000
   - 행 2: 보통예금(대변) 3,000,000
   - 적요: "신입사원 202412월 급여"

**4단계: 승인 워크플로우**
1. 승인 요청 (DRAFT → PENDING)
2. MANAGER 계정으로 로그인
3. 승인 (PENDING → APPROVED)
4. 전기 (APPROVED → POSTED)

**5단계: 검증**
1. 전표 상세에서 POSTED 상태 확인
2. 급여 계정 잔액 확인 (차변 +3,000,000)
3. 보통예금 계정 잔액 확인 (대변 +3,000,000)

**예상 결과**:
- ✅ 모든 단계가 순차적으로 성공
- ✅ 데이터 일관성 유지
- ✅ 계정 잔액 정확하게 반영

#### TC-E2E-002: 매출 거래 전표 입력 및 부가세 처리
**목적**: 복합 분개 플로우 검증
**권한**: USER (입력), MANAGER (승인)
**시나리오**:

**1단계: 매출 전표 입력 (USER)**
1. USER 계정으로 로그인
2. 전표 입력 폼 열기
3. 분개 라인 입력:
   - 행 1: 보통예금(차변) 1,100,000
   - 행 2: 매출(대변) 1,000,000
   - 행 3: 부가세예수금(대변) 100,000
   - 적요: "제품 판매 (부가세 포함)"
4. 저장 (상태: DRAFT)

**2단계: 승인 요청 (USER)**
1. 전표 상세에서 "승인 요청" 클릭

**3단계: 승인 (MANAGER)**

3. 해당 전표 승인
4. 상태 확인: APPROVED

**4단계: 전기 (MANAGER)**
1. "전기" 버튼 클릭
2. 경고 메시지 확인
3. 전기 실행
4. 상태 확인: POSTED

**5단계: 잔액 검증**
1. 보통예금: 차변 +1,100,000
2. 매출: 대변 +1,000,000
3. 부가세예수금: 대변 +100,000
4. 대차평형 확인

**예상 결과**:
- ✅ USER가 전표 입력 가능
- ✅ 승인 권한 분리 (USER는 승인 불가)

- ✅ 부가세 계정 정확하게 반영

#### TC-E2E-003: 오류 전표 반려 및 재입력
**목적**: 전표 반려 후 수정 플로우 검증
**권한**: USER (입력), MANAGER (반려)
**시나리오**:

**1단계: 오류 전표 입력 (USER)**
1. USER 계정으로 로그인
2. 전표 입력:
   - 행 1: 현금(차변) 500,000
   - 행 2: 잘못된 계정(대변) 500,000
3. 승인 요청

**2단계: 전표 반려 (MANAGER)**
1. MANAGER 계정으로 로그인
2. 전표 확인 후 "반려" 클릭
3. 취소 사유: "대변 계정 오류 - 매출 계정으로 수정 필요"
4. 반려 실행
5. 상태 확인: CANCELLED

**3단계: 새 전표 재입력 (USER)**
1. USER 계정으로 다시 로그인
2. 반려된 전표 내용 참고하여 새 전표 입력:

3. 저장 및 승인 요청

**4단계: 재승인 및 전기 (MANAGER)**
1. MANAGER 계정으로 로그인
2. 수정된 전표 확인
3. 승인 → 전기

**예상 결과**:
- ✅ 반려 사유가 기록되어 확인 가능
- ✅ 반려된 전표는 CANCELLED 상태로 보존
- ✅ 새 전표로 정상 처리
- ✅ 감사 추적 가능 (반려 이력 보존)

테스트 완료 후 다음 스크립트로 데이터 초기화:

```sql
-- 전표 데이터 삭제
DELETE FROM transactions WHERE company_id = {test_company_id};

-- 테스트 사원 삭제
DELETE FROM users WHERE email LIKE '%@test.erp.com';

-- 계정과목 잔액 초기화
UPDATE accounts SET debit_balance = 0, credit_balance = 0
WHERE company_id = {test_company_id};
```

### 9.2 테스트 계정 관리

- 테스트 후 테스트 계정은 삭제하지 않고 비활성화
- 다음 테스트를 위해 비밀번호 초기화
- 테스트 데이터는 주기적으로 백업
